# Status

This page is a snapshot of the repository's current state, replaced at every handoff. It is not a work log or an issue tracker. Work items live in [GitHub issues](https://github.com/ashuangiras/polaroid/issues).

**Development workflow ([#65](https://github.com/ashuangiras/polaroid/issues/65), [ADR-0031](../architecture/decisions/0031-scoped-verification-and-local-only-ci.md)):** a change is verified through the binding that matches it. `verify-docs`, `verify-records` and `verify-focused` call `dev.change.verify` v4 at a named scope; `verify-change` is the full gate. A full gate builds once per source state (`scripts/build.sh`), and every gate command runs once. Go's test cache applies except to `internal/archtest`, `internal/lifecycle` and `internal/recovery`. Hosted CI follows the `hosted-ci` binding, which is local-only: `ci` runs only on manual dispatch, and the release workflow no longer runs on pull requests. No binary changed, so nothing was released or upgraded.

## Implemented

- **Procedures:** a stable UUIDv7 ID and a unique canonical key, enforced by a `UNIQUE` constraint, with a `409 canonical_key_exists` response for duplicates.
- **Versions:** version 1 is stored atomically with the procedure. Philosophy, method and revision reason are typed text. Contract and instructions are free-form JSON objects, checked for shape only.
- **Revisions:** a revision is appended only against the latest `base_version`. Any other base gets `409 version_conflict`, which includes `latest_version`. Of several concurrent revisions from the same base, exactly one succeeds.
- **Immutability in the database:** triggers reject `UPDATE` and `DELETE` and non-contiguous version numbers. `CHECK` constraints enforce JSON objects and the canonical-key format.
- **Bindings** ([#1](https://github.com/ashuangiras/polaroid/issues/1), [ADR-0007](../architecture/decisions/0007-repository-identity-for-bindings.md)):
  - a binding has a stable UUIDv7 ID, a repository identifier in canonical-path form, a local name, and the procedure ID. `(repository, name)` is unique (`409 binding_exists`);
  - binding revisions hold `inputs` (a free-form JSON object), a `version_policy` of `{"pin": N}` or `{"contextual": {}}`, and a reason. They are appended against `base_revision` (`409 revision_conflict` with `latest_revision`);
  - an unknown procedure gets `404`, and a pin to a missing version gets `400` naming `revision.version_policy.pin`;
  - contextual policies are stored and returned verbatim. `GET /v1/bindings/{id}/resolution?environment=…` resolves the latest revision from evidence (#13);
  - migration `0002` adds the tables with immutability, contiguity and pin-existence triggers. A schema-version-1 database is upgraded in place.
- **Subprocedure references** ([#2](https://github.com/ashuangiras/polaroid/issues/2), [ADR-0008](../architecture/decisions/0008-subprocedure-references.md)):
  - a version may carry `references`, each with a unique `name`, a target `procedure_id`, a `version_policy` (the binding type), and `inputs` that map each child input to `{"input": "<parent input>"}` or `{"value": <JSON>}`;
  - an unknown target, a missing pinned version, a duplicate name or a malformed mapping gets `400`, with every failing reference named in `fields`;
  - references are returned in order, byte-for-byte. A version without references has no `references` field, so older versions are served unchanged;
  - migration `0003` stores references in `procedure_version_references`. A trigger and a deferred foreign key allow them only in the transaction that creates their version, and triggers make them immutable and check pinned versions.
- **Composition graph** ([#3](https://github.com/ashuangiras/polaroid/issues/3), [ADR-0009](../architecture/decisions/0009-reference-graph-rules.md)):
  - a pinned reference selects its pinned version. Without a resolution context, a contextual one selects the target's latest version; the write-time check always does;
  - every write of a version with references expands its graph in the write transaction. A path that reaches a procedure already on it, at any version, gets `409 reference_cycle` with the `cycle` path, and nothing is stored. This covers `A → A`, `A → B → A`, a cycle closed by a later revision of a target, and two concurrent half-cycles (exactly one is stored);
  - limits are a depth of 32 and 2048 nodes. Beyond them the response is `422 graph_too_large`, never partial data;
  - `GET /v1/procedures/{id}/versions/{n}/graph` (CLI `graph ID N`) returns the nested tree with the exact version of every node, read from one snapshot.
- **Execution records** ([#7](https://github.com/ashuangiras/polaroid/issues/7), [ADR-0010](../architecture/decisions/0010-execution-records.md)):
  - an execution is written once after a run and never changed. It records:
    - the exact procedure `version`, and an optional binding revision;
    - the `repository` and a full commit hash (40 or 64 lowercase hex characters);
    - a named `environment` with free-form attributes;
    - the effective `inputs`;
    - an `outcome` of `succeeded` or `failed`;
    - non-empty inline `evidence`;
  - an unknown procedure or binding gets `404`. These get `400` naming the field: a missing version or binding revision, a binding of another procedure or repository, and a version other than the binding revision's pin;
  - `POST /v1/executions`, `GET /v1/executions/{id}`, and `GET /v1/executions?procedure_id=…[&version=…][&repository=…]`, which returns summaries oldest first. CLI commands: `record`, `get-execution`, `executions`;
  - migration `0004` adds the table, with foreign keys to the version and binding revision, a binding-consistency trigger, `CHECK`s on the commit, environment, outcome and JSON fields, and immutability triggers.
- **Subprocedure executions** ([#9](https://github.com/ashuangiras/polaroid/issues/9), [ADR-0011](../architecture/decisions/0011-subprocedure-executions.md)):
  - a parent execution lists `children: [{reference, execution_id}]`, naming executions recorded earlier. A child must:
    - fulfil a reference of the parent's version;
    - have run that reference's target, at exactly the pinned version for a pinned reference (any version for a contextual one);
    - share the parent's repository and commit;
  - each reference has at most one child, and each execution has at most one parent. Every violation is `400` naming `children[i].reference` or `children[i].execution_id`;
  - concurrent parents cannot claim the same child: exactly one succeeds. Trees nest, and `children` is omitted when empty, so earlier executions are served unchanged;
  - migration `0005` adds `execution_children`. A trigger and a deferred foreign key allow links only in the parent's transaction, a trigger checks each link against its reference, and links are immutable.
- **Verification** ([#11](https://github.com/ashuangiras/polaroid/issues/11), [ADR-0012](../architecture/decisions/0012-derived-verification.md)):
  - derived on read from executions and links. Nothing is stored and there is no migration; each read is one snapshot (one transaction);
  - an execution is verified when it succeeded and every reference of its version has a linked, verified child, recursively. Otherwise it reports its direct problems: `outcome_failed`, `missing_child`, `child_not_verified`;
  - a combination is repository, commit, `environment.name`, canonical inputs (sorted members, RFC 8785 floats, exact integers) and the child-version tree. Its status is that of its latest execution;
  - `GET /v1/executions/{id}/verification` and `GET /v1/procedures/{id}/versions/{n}/verifications[?repository&commit&environment]`. CLI commands: `verification`, `verifications`.
- **Contextual resolution** ([#13](https://github.com/ashuangiras/polaroid/issues/13), [ADR-0013](../architecture/decisions/0013-evidence-based-resolution.md)):
  - a context is a repository and an environment name. A version is verified there when its latest execution there is verified; that execution is its evidence;
  - under a node with evidence, references follow the child executions it linked, so a verified combination is used as a whole. Otherwise a contextual reference selects the highest verified version, else the latest. A pinned reference selects its pin, with the pin's evidence if any;
  - edges report `selected_by` (`pin`, `evidence`, `latest`), and nodes with evidence report `verified_by`. Cycles and limits are still checked on read;
  - `GET /v1/procedures/{id}/versions/{n}/graph?repository=…&environment=…` and `GET /v1/bindings/{id}/resolution?environment=…`. CLI: `graph ID N REPO ENV`, `resolve BINDING_ID ENV`. Nothing is stored and there is no migration.
- **Selection evidence and target verification** ([#31](https://github.com/ashuangiras/polaroid/issues/31), [ADR-0018](../architecture/decisions/0018-selection-evidence-and-target-verification.md)):
  - every node with evidence also reports `selection_evidence`: the execution that selected it, with its repository, commit and environment. `verified_by` is unchanged, and means the same: a reason to select, not verification of any other commit;
  - the graph endpoint (with a context) and binding resolution accept an optional target, `commit` and `inputs` (the root's effective inputs) given together; HTTP query parameters, MCP arguments of the same names, and CLI `graph ID N REPO ENV COMMIT INPUTS` and `resolve BINDING_ID ENV COMMIT INPUTS`;
  - with a target, each node reports `target_verification` in the verification-list shape: its exact selected combination at the target (children's inputs through the reference mappings, the selected child-version tree), judged by that combination's latest execution. Selection is unchanged, nothing is inferred from ancestry or checkouts, and nothing is stored.
- **MCP server** ([#15](https://github.com/ashuangiras/polaroid/issues/15), [ADR-0014](../architecture/decisions/0014-mcp-transport.md), [contract](../architecture/mcp.md)):
  - `polaroidd` serves `/mcp` on its listener, behind the same loopback-host check and cross-origin protection: stateless streamable HTTP, JSON responses, protocols 2026-07-28 and 2025-11-25 ([ADR-0016](../architecture/decisions/0016-mcp-protocol-2025-11-25.md): the 2025-11-25 handshake issues no session; older revisions are never served), `ttlMs: 0` on every discover, list and read result (#20), 1 MiB bodies. Built on the official Go SDK v1.8.0;
  - 25 tools with full HTTP API parity (16 annotated read-only; #35 added `register_repository`, `add_repository_alias`, `get_repository`, `list_repositories` and `record_procedure_origin`; #37 added `snapshot` to `list_procedures` and `list_bindings`). Arguments are flat, named after record fields, decoded strictly (unknown and duplicate members rejected, member order kept); results and error bodies are the HTTP API's, as structured content and text; field errors use the flat names;
  - resource templates `polaroid://procedures/{id}`, `polaroid://procedures/{id}/versions/{version}` and `polaroid://bindings/{id}`;
  - the record shapes, strict decoding and error classification moved into `internal/transport/wire`, shared by both transports; the HTTP tests pass unchanged against it.
- **Feedback box** ([#16](https://github.com/ashuangiras/polaroid/issues/16), [ADR-0015](../architecture/decisions/0015-feedback-reports.md)):
  - an immutable report about Polaroid itself: `kind` (`problem` or `suggestion`), a single-line `summary` (every Unicode line terminator rejected), `details`, a canonical-key `reporter`, and an optional free-form `context`, stored as `{}` when absent. No triage state; reading or writing one changes no other record;
  - `POST /v1/feedback`, `GET /v1/feedback/{id}` and `GET /v1/feedback[?kind=…]` (oldest first, full reports, strict query). CLI: `feedback`, `feedbacks`, `get-feedback`. MCP: `report_feedback`, `list_feedback`, `get_feedback`; the server instructions now ask agents to report problems and suggestions;
  - migration `0006` adds the `feedback` table with `CHECK` constraints mirroring the field rules and immutability triggers.
- **Persistence:** SQLite in WAL mode with `synchronous=FULL`. Migrations are counted by `user_version`, and a database with a newer schema is refused.
- **HTTP API v1** ([contract](../architecture/http-api.md)):
  - procedures: create, list, get by ID, get by key, get one version, get a version's composition graph, revise, and `/healthz`;
  - bindings: create, list by repository, get with history, get one revision, revise;
  - JSON errors throughout, for invalid input, missing records, conflicts and internal failures;
  - strict decoding, a 1 MiB limit, a loopback-host check and cross-origin protection.
- **`polaroidd`:** `-addr` and `-db` flags or the `POLAROID_*` environment variables, loopback by default, server timeouts, and graceful shutdown on SIGINT or SIGTERM.
- **`polaroid` CLI:** a generic client. It reads JSON from a file or stdin, prints response bodies to stdout, and exits with 0, 1 or 2. Binding commands: `bindings`, `bind`, `get-binding`, `get-binding-revision`, `revise-binding`.
- **Development procedures as records** ([#28](https://github.com/ashuangiras/polaroid/issues/28), [ADR-0017](../architecture/decisions/0017-development-procedures-as-records.md), [procedural-loop.md](procedural-loop.md)):
  - fixtures in `examples/development`: `go.module.build`, `go.module.checks` (version 1 is a labelled demonstration seed with one stale instruction; version 2 is the agent's correction, exported verbatim) and `dev.change.verify`, which references both contextually. `github.com/ashuangiras/polaroid` binds the parent with its commands; a fixture-only second repository binds the same procedure;
  - `scripts/load-fixtures.sh` loads them through the CLI, replacing canonical keys with service-assigned IDs, reusing identities, appending missing versions against the stored latest, and refusing to overwrite a differing version or binding revision;
  - `make demo` replays the loop with scripted outcomes, labelled as such. No product code changed; records.md now states that member order never splits a combination and array order does.
- **Target-aware development procedure** ([#33](https://github.com/ashuangiras/polaroid/issues/33), [procedural-loop.md](procedural-loop.md#target-aware-procedure-33)):
  - `dev.change.verify` version 2, appended through MCP with `base_version: 1` and exported verbatim to `examples/development/procedures/dev-change-verify/v2.revise.json`. - **Several repositories in one catalog** ([#35](https://github.com/ashuangiras/polaroid/issues/35), [ADR-0019](../architecture/decisions/0019-repository-registry.md), [ADR-0020](../architecture/decisions/0020-procedure-origin-and-applicability.md), [ADR-0021](../architecture/decisions/0021-targeted-feedback-and-bounded-lists.md)):
  - repositories are registered explicitly under a canonical identifier and name; other identifiers are added as aliases with a reason. An identifier belongs to one repository forever (`409 repository_identifier_exists`); nothing is registered implicitly or by the migration. Stored records keep the identifier they were written with, and are associated through the registry. Repository filters on lists match every identifier of a registered repository; binding names are unique across them (`409 binding_exists`). Verification and resolution still compare identifiers exactly;
  - origin (`repository_id`, `reason`) is recorded once per procedure, at creation or later (`409 origin_exists`). Each version may declare a `goal` and `applicability`, `{"shared": {}}` or `{"repository": "<id>"}`; versions without it are unspecified and apply everywhere, as before. Promotion or narrowing is a new version. A local version admits children applicable in its repository; other versions admit no local child. Bindings, binding revisions, executions and references are checked on write; contextual resolution considers only admitted versions;
  - feedback may name a `subject` (`service`, `repository`, `procedure`[+`version`], `binding`[+`revision`], `execution`) plus `repository` and `execution_id` context, checked for existence and consistency. Reports without a subject are about the service;
  - procedures filter by `repository`, `scope` and `q`; executions by any of procedure, version, repository and commit; feedback by subject and repository. Every list takes opt-in `limit` (1 to 500) and an opaque `after` cursor; without `limit` lists are complete, as before. Execution, feedback and repository times are assigned in the write transaction after every stored one, so pages never skip a later commit;
  - migration `0007` adds three immutable tables and nullable columns with consistency triggers, and updates no row. CLI: `register`, `alias`, `repository`, `repository-by-identifier`, `repositories`, `origin`, and `NAME=VALUE` parameters on list commands. The loader registers `repositories/*.json`, records `origin.json`, and replaces repository identifiers with IDs;
  - `make demo` step 19 runs fixtures A and B (`examples/multi-repository`), step 20 replays the exported development records, and step 23 upgrades a schema-6 database.
- **Identity, pages and scope labels** ([#37](https://github.com/ashuangiras/polaroid/issues/37), [ADR-0022](../architecture/decisions/0022-repository-identity-in-evidence.md), [ADR-0023](../architecture/decisions/0023-pagination-guarantees-and-scope-labels.md)), with no migration:
  - verification combinations, verification lists, target verification and contextual resolution match executions by registered repository identity; an unregistered identifier matches only itself. The latest execution across the identity's identifiers decides. An alias registered after executions joins them to its repository's combinations from then on; no record changes. Executions, selection evidence and combinations add `repository_id`; an execution's `repository` stays as submitted;
  - new cursors are bound to their list and parameters (`400` on `after` otherwise; older cursors still work). `snapshot=true` on the procedure and binding lists fixes membership and contents at the first page, using row-ID marks of append-only tables; live traversal is unchanged and documented;
  - versions and graph nodes report their own `scope`; procedure-level `scope` describes `latest_version` only;
  - `make demo` step 21 shows the alias effect, a snapshot traversal and the per-version scope, scripted.
- **Child inputs follow the reference mapping** ([#39](https://github.com/ashuangiras/polaroid/issues/39), [ADR-0024](../architecture/decisions/0024-child-inputs-follow-the-reference-mapping.md)), with no migration:
  - a child link is accepted only if the child's `inputs` equal the reference's mapping applied to the parent's `inputs`, compared canonically (member order, RFC 8785 numbers, exact integers); no subset or override, and an empty mapping requires `{}`. Otherwise `400` naming `children[i].execution_id`, with both inputs in the message. The child's environment may still differ;
  - stored links are served unchanged; a mismatched one reports `child_inputs_mismatch` (plus `child_not_verified` if the child is unverified) and never verifies its parent, nor any ancestor. Combination status, contextual selection and target verification follow;
  - one domain implementation (`mappedInputs`: the mapping target verification uses, then the combinations' canonical form) serves writes and reads. The database does not enforce the rule: a trigger cannot reproduce the canonical comparison, so a link written with direct SQL can be stored, but never verifies;
  - `make demo` step 22 shows a build of a dirty tree refused for a parent claiming a clean one, over HTTP and MCP; `make e2e` and `make e2e-mcp` each add a refusal check.
- **Per-user catalog** ([#41](https://github.com/ashuangiras/polaroid/issues/41), [ADR-0025](../architecture/decisions/0025-per-user-default-database.md)), with no schema change:
  - the default database is `<home>/.polaroid/data/polaroid.db`, with the home from `os.UserHomeDir`; `-db` > `POLAROID_DB` > default; explicit relative paths keep their meaning. An empty `-db`, a set but empty `POLAROID_DB`, and a home that is unknown, relative or missing are errors naming the remedy; there is no fallback to the working directory;
  - for the default location only, missing `.polaroid` and `data` directories are created `0700` and a missing database `0600` before SQLite opens it, so `-wal` and `-shm` are `0600` too (the driver would create all three `0644` under umask `022`). Existing entries and explicit paths are never chmod-ed; exposed default entries get a start-up warning. The start-up line logs `db` and `db_source` (`flag`, `environment`, `default`);
  - `scripts/migrate-catalog.sh SOURCE [HOME]` moves a stopped catalog: refuses an occupied destination (exit 3) or an open source, SQLite online backup into `backups/` (committed WAL content included), integrity and foreign-key checks, a private restore, equal dumps, a no-replace link into place; source and backup are kept;

- **Packaged smoke test under any temporary directory** ([#52](https://github.com/ashuangiras/polaroid/issues/52)), no product, schema or API change:
  - **The defect:** `smoke-test.sh` compared the database path as typed (`$TMPDIR/polaroid-smoke.X/data/smoke.db`) with the start-up line's `db=` value. `polaroidd` logs that value as the clean absolute path (`filepath.Abs`), quoted by slog when it holds a space or `=`. A `TMPDIR` ending in `/` (the macOS per-user directory) or containing spaces therefore failed "the start-up line names the temporary database", although `polaroidd` opened the right database.
  - **The fix:** the script names the database as `polaroidd` reports it (`WORK=$(cd "$WORK" && pwd -P)`), and the check requires that exact path in either of slog's encodings.
  - **Regression coverage:** `scripts/smoke-archive-check.sh DIR` runs an extracted archive's own smoke test under the platform's normal `TMPDIR` and a `TMPDIR` with spaces. - **Catalog backup, inspection and restore** ([#56](https://github.com/ashuangiras/polaroid/issues/56), [ADR-0030](../architecture/decisions/0030-catalog-backup-and-restore.md)). There is no schema, HTTP or MCP change, and the CLI changes are additive:
  - **`polaroid backup [-db FILE] [-dir DIR]`:**
    - takes a `VACUUM INTO` snapshot, which includes committed `-wal` content while writers continue;
    - validates it (integrity, foreign keys, schema);
    - writes versioned `backup.json`: source, time, reason, schema, build, size, SHA-256 and row counts;
    - publishes `polaroid-<UTC time>[-pre-restore][-N]` from a private staging directory under `~/.polaroid/backups` (`0700`; the database is `0600`) by one non-overwriting rename, then reads it back;
  - **`polaroid inspect-backup BACKUP`:** read-only and immutable; exit 0 when valid, 1 when not;
  - **`polaroid restore [-db] [-dir] [-plan] [-replace] [-wait] BACKUP`:**
    - `-plan` is read-only and reports the backup, destination, service state, migration, actions and blockers;
    - refuses (exit 3, nothing changed) an invalid backup, a newer schema in the backup or the destination, a missing `-replace`, a managed service that is neither running nor stopped or whose endpoint another process holds, and `-wal`/`-shm` beside an unmanaged catalog (an advisory check);
    - order: stage, check SHA-256, migrate an older backup, validate; stop the managed service; take a validated pre-restore recovery backup; keep the current catalog as `<db>.pre-restore-<time>`; rename the staged copy over the catalog (atomic); sync; restart and wait until healthy; roll back to the original, keeping `<db>.failed-restore-<time>`, if it does not start, but only once the lifecycle stop confirms shutdown: stopped, no other endpoint holder, no `-wal`/`-shm`, live context ([#59](https://github.com/ashuangiras/polaroid/issues/59)). Otherwise nothing is renamed or removed: the outcome is `rollback-blocked` (exit 1), with `original`, `kept` and `manual_recovery`;
  - catalog selection: `-db`, then `POLAROID_DB`, then the installed service's catalog, then the default. `cmd/polaroid` reaches storage only through the new `internal/recovery`, which `internal/archtest` enforces;
  - coverage: Go tests (a WAL snapshot with concurrent writes, read back through the HTTP API; every injected failure; 15 of 15 mutations caught), a new `make e2e` section, `make lifecycle` [13] against the real launchd and systemd, and the packaged smoke test (42 checks);
  - `scripts/smoke-archive-check.sh` now identifies leftover daemons by executable and arguments; `pgrep -f` matched its own decoy, which falsely reported leftover daemons;
  - procedures: `polaroid.operations.change` v1 is new; `polaroid.service.manage` v3 backs up with `polaroid backup` and restores with `polaroid restore`.
- **Supporting material:** example records, the live demo (`make demo`, now including a two-repository binding and the procedural-loop replay), the end-to-end scripts (`make e2e`, `make e2e-mcp`; run by `make ci` and CI with the interop checks off since [#27](https://github.com/ashuangiras/polaroid/issues/27)), package-boundary tests, a dependency and license gate, CI workflow, Copilot instructions, and the docs and ADRs.
