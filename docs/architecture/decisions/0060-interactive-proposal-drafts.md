# 0060. Interactive, field-by-field proposal construction: `propose_start`/`propose_advance`

**Status:** Accepted (Grounded publication M3; amends [ADR-0059](0059-grounded-publication.md) Part 2 additively — `propose` itself is unchanged).
**Date:** 2026-10-17

## Context

The owner's original request for agent-proposed knowledge was explicitly modeled on `start`/`advance` (ADR-0053): *"Polaroid can pose this as a question to agent... then the agent would be able to record it... start publishing and advance each item, verify it and store it."* [ADR-0059](0059-grounded-publication.md) kept the "agent and Polaroid only, no operator" half of that request, but silently dropped the interactive half in favor of a single-shot `propose` call — every field given up front, one commit-or-reject response. This was never a deliberate, surfaced trade-off; it was found only when manually demonstrating the shipped feature and asked about directly.

Separately, a real gap exists in what `propose` (and `Kernel.publish` generally) can express today: [ADR-0057](0057-typed-record-completeness.md)'s completeness bar requires only *at least one* of `requires`/`preconditions`/`postconditions`; nothing distinguishes a field that is empty because an author deliberately considered it and found nothing to say, from one that is empty because nobody ever thought about it. The corpus already has exactly one precedent for recording that distinction: `OutputsComplete` (a bool, read by `Compose`: `p.OutputsComplete && !slices.ContainsFunc(p.Outputs, ...)` turns an "undetermined" input-matching finding into a firm "missing" one). Generalizing that one field's pattern to the other content fields closes both gaps at once: it gives `propose_start`/`propose_advance` something concrete to ask about, and it gives the corpus an honest, auditable record of which fields were actually reviewed.

## Decision

**Four new boolean fields on `Procedure`**, one per existing content list, mirroring `OutputsComplete` exactly: `PreconditionsComplete`, `PostconditionsComplete`, `InvariantsComplete`, `InformalConditionsComplete`. `true` means "this list is deliberately complete as given, confirmed by whoever last reviewed it" (possibly empty); `false` (the default, and the only value any pre-existing Procedure has) means "not reviewed this way" — the status quo, completely unaffected. **No reasoning-semantics change in this milestone**: unlike `OutputsComplete`, these four are not yet read by `Compose`, `resolve`, or any other reasoning code — purely stored and returned by `read`/`resolve` like any other scalar. Wiring them into composition's own established/contradicted/missing logic (the natural next step, symmetric with how `OutputsComplete` already works) is explicitly deferred to a later, separate decision.

**A new ephemeral concept, a Draft** (`internal/memory`, its own SQLite table, the same shape and guarantees `Walkthroughs` already established in ADR-0053: a UUIDv7 token, a sliding TTL, per-field fold over an append-only event log, never kept forever, not counted by `discover(kind="stats")`, no trace once expired or closed): one agent's in-progress construction of a single proposal, scoped in this milestone to **an existing Procedure only** — `new_concept`/`new_claim` have one field each and no silent-absence problem, `new_orchestration` needs no citation or review at all; extending Drafts to those shapes is explicitly deferred, not forbidden, pending real evidence it's needed.

**`propose_start`**: `key` (an existing Procedure), `proposer`, `rationale`. Polaroid computes the target's own undecided reviewable fields — `preconditions`, `postconditions`, `invariants`, `informal_conditions`, in that fixed order — skipping any field that is already non-empty *or* already marked `*Complete` from an earlier publish. Returns `{token, snapshot, next_field, status}`: if a field remains, `status` is `"in_progress"` with `next_field` naming it. If nothing was left undecided at all (every field already complete on the record), `propose_start` attempts the real commit immediately, in the same call, through the identical path `propose_advance`'s own auto-commit uses (an edge case, expected to be rare in practice): `status` is `"complete"` with the new `snapshot`/`key` on success, or the specific commit error on failure, with the draft left open for `propose_advance` to retry. (Implementation note: an earlier draft of this decision described a third status, `"ready"`, for "nothing left undecided, not yet committed." The shipped implementation never needs it — `Start` always attempts the commit rather than stopping one step short — so only `"in_progress"` and `"complete"` exist, matching `propose_advance`.)

**`propose_advance`**: `token`, and exactly one of — an **answer** for the named field, `{field, values, citations}` (grounded exactly as single-shot `propose` already requires: every citation's quote must appear verbatim in the new content), or an explicit **decline**, `{field, confirmed_absent: true, reason}` (no citation needed: this is the agent's own testimony that the field genuinely does not apply, the same epistemic category ADR-0056 already established for `blocked`/`escalate` — Polaroid never verifies it, only records it, and sets that field's `*Complete` to `true` with an empty list). Folds the answer per field (the same latest-wins-per-key fold `advance` already uses for walkthrough outcomes): a later answer for the same field simply replaces an earlier one.

**Automatic commit attempt.** The moment every reviewable field is decided (by an answer, a decline, or having been already non-empty/`Complete` at `propose_start`), the same `propose_advance` call that supplied the last answer immediately attempts the real commit: `Proposer`'s own already-shipped three checks (citation self-consistency per supplied field, #173's non-vacuous composition gate scoped to this key, and the novelty-diff), through the same `Kernel.Publish` path. Success returns `{snapshot, key}`; the token then behaves exactly like a closed or expired one (`not_found`, no trace — ADR-0055's rule, reused unchanged). **Failure does not close the Draft**: a still-vacuous composition or a redundant result is returned as the specific error, and the Draft stays open, every field's answer intact, so the agent can correct exactly the field responsible (for example, replacing a `confirmed_absent` decline with a real postcondition) and call `propose_advance` again.

**`close: true`** on `propose_advance` ends the Draft immediately, abandoned, whatever its status — identical to ADR-0055's `close` for walkthroughs.

**Single-shot `propose` (ADR-0059, `/mcp/agent/v4`) is completely unchanged and stays.** It is faster for an agent that already has a fully-formed, correct addition ready, and remains the only way to propose `new_concept`/`new_claim`/`new_orchestration`. It gains four new, optional, directly-settable arguments on `existing_procedure` (`preconditions_complete`, `postconditions_complete`, `invariants_complete`, `informal_conditions_complete`) for an agent that already knows the answer and does not need prompting — but **single-shot `propose` never infers or defaults any of these to `true` on its own**; omitting them leaves the status quo (`false`, not reviewed this way) exactly as every pre-existing Procedure already has it. This is deliberate, not an oversight: forcing every single-shot call through the slower, field-by-field path to get the stronger completeness guarantee would defeat the purpose of having a fast path at all; the four new flags are simply how a corpus consumer can later tell which route a given field's current state came through.

**Mounted at a new `/mcp/agent/v5`**: the same seven `/mcp/agent/v4` tools, unchanged, plus `propose_start`/`propose_advance` — following the exact precedent `resolve`/v2, `start`/`advance`/v3, and `propose`/v4 each already set for adding a capability without touching a frozen prior version.

**Explicitly not decided here:**
- Wiring `*Complete` into `Compose`'s own established/contradicted/missing reasoning (the natural generalization of `OutputsComplete`'s existing use) — a separate, later decision, once there is real data to show whether it changes reasoning outcomes usefully.
- Extending Draft-based interactive construction to `new_concept`, `new_claim` or `new_orchestration` — deferred pending evidence it's needed; none of the three has more than one field or a silent-absence problem today.
- Any operator-facing visibility into open Drafts (`list`/`get`, the way walkthroughs eventually got one in ADR-0056, Milestone 5) — deferred the same way, until real usage shows a debugging need.
- Any rate limit on `propose_start`/`propose_advance` calls.

## Consequences

- The owner's original `start`/`advance`-shaped request for proposing knowledge is now actually built, not just gestured at; single-shot `propose` (ADR-0059) remains available and unaffected for the case it already serves well.
- Every `Procedure` record gains four new, optional boolean fields; every record published before this milestone reads back with all four `false` ("not reviewed this way"), exactly the same backward-compatible default `OutputsComplete` already established.
- A corpus consumer can now distinguish, per field, three states: has real content; confirmed, reviewed, and genuinely empty; or simply never considered — closing the exact "presence without teeth, without even knowing it's missing" gap this whole initiative (ADR-0059) was opened to address, one level deeper.
- `/mcp/agent` gains a second write capability (`propose_start`/`propose_advance`), alongside `propose` itself; both remain narrowly scoped to what Polaroid can mechanically check without a human, the same discipline ADR-0059 already established.
