# 0048. Git-native agent interface, finalized: `/mcp/agent` on living knowledge, and an explicit operator surface

**Status:** Accepted; `/mcp/agent` remains **experimental** (ADR-0043), now on its Git-native form. `/mcp` is unaffected and stays under ADR-0038's v1 compatibility guarantee: unchanged, still 40 tools (25 read-only, 15 write).
**Date:** 2026-10-13

## Context

ADR-0043 built agent mode on the legacy, versioned SQLite path (`internal/memory`) as an interim step, already promising that its interface would change once the Git-native knowledge path (ADR-0044–0047) was ready. That foundation now exists: a kernel that publishes, reads and resolves a complete catalog by canonical key at an opaque snapshot token (ADR-0045), synchronisation between independent instances over ordinary Git remotes with explicit fetch/validate/activate/push steps (ADR-0046), and the typed identities a feedback report and a publication need to refer to each other safely (ADR-0047). Milestone D's task is to make agent mode use this path as its sole procedural-knowledge authority, and to give operators an explicit, authorised way to drive it, without touching `/mcp`, the legacy record contract, or the package boundaries that keep the two paths apart.

## Decision

1. **Agent mode is rebuilt on the kernel, not on `internal/memory`.** `discover`, `read` and `feedback` take and return only a canonical key and an opaque snapshot token (`internal/transport/wire`'s `Knowledge*` shapes): no `procedure_id`, `version`, `binding`, `selected_by` or `latest_version` anywhere. `read` resolves one level — a reference's own references are read with a further `read` call — and accepts an optional snapshot to pin exactly what was served; omitted, it reads the active knowledge. `discover` and `read` of an empty catalog are a well-formed, explicit result (`"empty": true`), never an error: Git-native knowledge may start empty even where the legacy catalog already holds procedures (no migration in this milestone; see Consequences).
2. **A new orchestration package, `internal/knowledgeops`,** is the only thing between the transports and the knowledge path. `Agent` implements discover/read/feedback; `Operator` implements the explicit, operator-only surface below. It may import `internal/knowledge`, `internal/knowledgesync`, `internal/gitcore` and `internal/memory` (for feedback); nothing above it in either transport may import those domain packages directly (`internal/archtest`). `internal/transport/mcp` instead declares its own `AgentKnowledge` interface, expressed only in `wire.Knowledge*` types, that `knowledgeops.Agent` satisfies structurally — the MCP package's dependency footprint is unchanged.
3. **Feedback keeps using the legacy operational store (`internal/memory`), by design.** A finding is about living knowledge, but it is still an immutable, queryable report with resolution tracking; ADR-0047 already decided not to add a first-class "knowledge" subject type in this milestone. Agent-mode feedback is recorded with no `Subject` (service-level) and its `FeedbackRef{Key, Snapshot}` encoded under a reserved `"knowledge"` member of the report's free-form `Context`, confirmed real (`Kernel.CheckFeedbackRef`) before it is stored.
4. **A new, explicit, token-guarded operator surface, `internal/transport/httpops` at `/v1/knowledge/*`.** It is reached only through `knowledgeops.Operator`, never storage or the legacy API directly (`internal/archtest`). Every request, including reads, must carry the daemon's generated operator token in `Polaroid-Operator-Token`: binding to loopback is not treated as sufficient authorisation, since other local processes can reach a loopback-bound port too. Endpoints: `GET status`, `POST publications` (publish a proposal, with an optional `finding` that triggers reconciliation), `POST sources/{name}/fetch|validation|activation|push`, `GET activations`, `POST reconciliations/{finding_id}`. There is no scheduler: every operation is triggered by an explicit request. `cmd/polaroid` gets matching `knowledge-*` commands, sending the token from `$POLAROID_KNOWLEDGE_TOKEN`.
5. **Feedback-to-publication reconciliation is independent and idempotent.** `Operator.Reconcile(findingID)`: if the report is already resolved, say so; otherwise decode its `FeedbackRef`, search the knowledge history for a publication whose `Polaroid-Finding` trailer matches, whose `Changed` list includes the report's key, and whose origin is `OriginLocal` (an imported, activated publication never counts as locally verified feedback resolution — ADR-0047); if found, resolve the report as addressed with a `PublicationRef` (`polaroid-knowledge:<instance>/<snapshot>#<key>`) external reference; if not, report `no_publication_yet`, not an error. `Publish` with a `finding` calls the same path immediately after publishing, so the common case needs one request; a failed reconciliation never undoes the publication, which already succeeded, and is reported in the publish result for a later, independent retry — `Reconcile` is safe to call again after a restart or an interruption.
6. **Explicit migration boundary.** The daemon opens a Git-core repository at `~/.polaroid/data/knowledge` by default (`-knowledge-dir` / `POLAROID_KNOWLEDGE_DIR`, mirroring ADR-0025's database convention) and loads a trust policy from a sibling `knowledge-sources.json` (`knowledgesync.LoadPolicy`; a missing file is an empty policy, not an error). This milestone migrates no legacy SQLite procedure into it. If the knowledge path cannot start (for example, the directory cannot be created), the daemon logs why and serves the legacy API and full-mode MCP unaffected; `/mcp/agent` and `/v1/knowledge` are simply not mounted. `GET /v1/knowledge/status` and agent mode's explicit empty result are how each interface's readiness is told apart.

## Consequences

- The full-mode tool contract is unchanged: `TestFullModeToolContract` and `TestFullModeContractIsDocumented` still hold 40 tools, 25 read-only and 15 write, with no new tool, field, or behaviour.
- `internal/transport/http` and `internal/transport/mcp`'s existing boundaries (forbidding `internal/knowledge`, `internal/knowledgesync`, `internal/gitcore`) are untouched; `internal/knowledgeops` and `internal/transport/httpops` are new, narrowly-scoped packages that carry the new dependency edges instead, so legacy writes can never be silently redirected into Git-core and nothing writes knowledge to both stores.
- An agent using only `/mcp/agent` never sees a procedure version, a binding, a selection rule, or anything Git-shaped: it discovers and reads by key and snapshot, and reports feedback the same way. An operator using `/v1/knowledge` or `polaroid knowledge-*` performs every Git operation explicitly; there is no automatic fetch, activation or push.
- Credentials for `fetch` and `push` are supplied per call (`gitcore.Credentials`, embedded in the request body) and never stored, logged, or echoed back; the trust policy file itself never holds them (ADR-0046).
- Not decided here: migrating existing SQLite procedures into Git-native knowledge, a first-class "knowledge" feedback subject type, and whether `/mcp/agent` is finalized (dropped from "experimental") — all left to a later milestone (E).
