# 0053. Stateful, expiring walkthroughs at a new `/mcp/agent/v3` (Guided Procedures, Milestone 2)

**Status:** Accepted (Milestone 2 of the initiative [ADR-0052](0052-ordered-sibling-steps.md) opened; depends on its `precedes` relation and `resolve`'s `plan`). Amended by [ADR-0054](0054-multi-level-plans.md): `advance`'s `outcome` additionally accepts a `path`, for a leaf found through a composed child; a bare `key` keeps its meaning here unchanged. Amended by [ADR-0055](0055-walkthrough-completion.md): `start`/`advance` gain a `status` member and `advance` gains a `close` argument, both additive. Amended by [ADR-0056](0056-walkthrough-visibility-and-status.md): `advance`'s outcome vocabulary gains `blocked`, and `start`/`advance` gain an `expand` argument.
**Date:** 2026-10-15

## Context

[ADR-0052](0052-ordered-sibling-steps.md) gave `resolve` a stateless `plan`: ordered sibling steps, with status derived from a `completed` list the caller resends every call. That validates the ordering idea cheaply, but it does not give an agent anything across genuinely separate sessions — an agent whose own context is gone has no `completed` list to resend. Delivering on that needs Polaroid itself to remember progress: a real, if deliberately small, persisted concept new to this system.

Every other record Polaroid keeps is either immutable history (procedure versions, executions, feedback) or append-only revisions with a "latest wins" current state (toil items, bindings, lifecycle events) ([records.md](../records.md)), and every one is kept forever — ADR-0036 already named that growth as an open, unresolved concern for the catalog overall. A walkthrough is a different kind of thing: per-agent runtime scratch state about one attempt at one procedure, not published knowledge, not audit evidence, and routinely abandoned (a changed plan, a retried task, a session that simply ends). Keeping every one forever would make this the single largest source of unbounded, low-value growth in the catalog.

Agent mode's own stated premise, repeated for both `/mcp/agent` and `/mcp/agent/v2`, is "no scheduler... an agent only discovers, reads and reports feedback." A stateful walkthrough is the first thing in agent mode that behaves like a scheduler, even in miniature. Rather than quietly stretch that premise a second time at `/mcp/agent/v2` (which already stretched it once, for `resolve`'s reasoning), this ADR gives it its own clearly labeled endpoint.

## Decision

**A new endpoint, `/mcp/agent/v3`**, the same transport rules as every `/mcp/agent*` endpoint, serving the unchanged `discover`, `read`, `feedback` and `resolve` (identical schemas to v2, the same invariant `cmd/polaroidd/e2e_corpus_test.go` already checks between v1 and v2, extended to v3), plus two new tools.

**`start`**: `goal` (required), `repository` and `context` (optional, same meanings as `resolve`). Resolves `goal` at the currently active snapshot and **pins it** for the walkthrough's lifetime, the same guarantee `discover`'s and `read`'s snapshot tokens already give — so a walkthrough's plan stays stable even if new knowledge is published or activated while it is open. Creates a new walkthrough identity and returns `{token, snapshot, plan}`: `plan` is exactly `resolve`'s `plan` member (ADR-0052) with an empty `completed` (nothing reported yet). A `goal` that is `not_found` or `not_applicable` in `repository` fails the same way `read` already does; a `goal` without `composes` is not an error — it starts with an empty, trivially complete `plan`.

**`advance`**: `token` (required), `outcome` (optional: `{key, status: "done"|"skipped"|"escalate", note?}`) and `context` (optional, folded into what the walkthrough has reported so far). Without `outcome`, this is a pure peek: the current `plan`, unchanged — deliberately not a third tool, since "what's my status" and "here's what I did" are the same shape of answer. `outcome.key` must be one of the goal's immediate composed children; any key is accepted, not only the current `next` (an agent may legitimately already know a later step is satisfied), but a key outside the goal's composed children is `invalid_request`. Returns the updated `{token, snapshot, plan}`.

**Identity.** A token is a UUIDv7 ([internal/memory](../../../internal/memory) already uses `uuid.NewV7()` for every record identity — executions, feedback, bindings, repositories, procedures; this follows the same convention), opaque to the caller, independent of any other walkthrough: no lookup by `(repository, goal)`, no uniqueness constraint, so two agents (or two attempts) can work the same procedure concurrently without colliding. Resuming across sessions depends entirely on the caller having kept its token; Polaroid offers no other way to find one.

**Persistence is new storage, in SQLite (`internal/memory`), not Git-native knowledge** (it is per-agent runtime state, never published or shared content): a new table of walkthrough events, one row per `start` or `outcome`-bearing `advance`, each naming its token, the reported `key`/`status`/`note`/`context` (or nothing, for the creating `start` event), and a timestamp. **Current state folds the event log per key, not per call**: for each composed child, its current status is whichever outcome was *last* reported for that specific key (a later `done` overrides an earlier `escalate` for the same key; reporting the same status again is harmless and idempotent); keys never reported stay pending. This is neither "latest wins" the way toil revisions or lifecycle events are (one row is not the whole current state) nor a plain union (one key cannot be simultaneously `done` and `escalate`) — it is a genuinely new persistence shape in this codebase, a per-key fold over an append-only log.

**`escalate` freezes `next` on that key.** `next` is the first composed child, in `precedes` order, that is not `done` or `skipped`; a child currently `escalate` counts as not-done for this purpose, so `next` stops there and does not advance past it, the same way a step whose own obligations are undecided already keeps `resolve`'s `unknowns` from being exhaustive (ADR-0052). It stays frozen until a later `advance` reports `done` or `skipped` for that same key, overriding the escalation per the fold rule above; nothing but another explicit report ever clears it; Polaroid does not time out or auto-resolve an escalation, TTL expiry aside.

**Expiry is real, and sliding.** Each event (including a no-`outcome` peek) resets the token's expiry to now plus a fixed TTL (the exact duration is an implementation detail set at build time, not re-litigated per call); `advance` or `start` on an expired or unknown token both fail `not_found` — the unknown case because there is nothing to distinguish, and the expired case because, deliberately, Polaroid keeps no trace of an expired walkthrough to report anything more specific about: expiry means gone, not "gone, but here is a record that it once existed." This is the first record in Polaroid that is not kept forever; nothing else in the catalog is affected, and catalog statistics (ADR-0036) do not count walkthroughs — they are runtime state, not catalog content.

**No operator-facing visibility in this milestone.** Every other record type has a `list`/`get` surface; a walkthrough deliberately does not, in Milestone 2. It is bounded by its own TTL without needing operator intervention, and building visibility tooling for ephemeral per-agent scratch state ahead of any evidence it is needed would be speculative. A later milestone can add it if usage shows a real debugging need.

**Explicitly not decided here:**
- The exact TTL duration (an implementation parameter, chosen and documented when this is built, not a governed, versioned policy like write limits).
- Whether `start` should refuse a `goal` whose `plan` is already a cycle-free, zero-length empty list (today: allowed, trivially complete) — may be revisited if it proves confusing in practice.
- Any operator surface, retention reporting, or cross-walkthrough querying.
- Multi-level plans (unchanged from ADR-0052: one level only).

## Consequences

- Agent mode now has three endpoints with three different, clearly labeled levels of capability and risk: `/mcp/agent` (no reasoning, no state), `/mcp/agent/v2` (reasoning, still no state), `/mcp/agent/v3` (reasoning and state, bounded by a TTL). Each is additive; none changes the others' tools, schemas or guarantees.
- Polaroid gains its first record kind that is not kept forever and not immutable history — a deliberate, narrow exception, justified by what this data actually is (ephemeral per-agent scratch state), not a general loosening of the immutability or retention principles elsewhere in the catalog.
- `/mcp/agent/v3`'s stability is a new compatibility surface once released, under the same v1 guarantee ADR-0038 already extends to every agent-mode endpoint; this ADR does not itself declare it finalized (the same "experimental until explicitly finalized" path ADR-0043 and ADR-0048 took for `/mcp/agent`, resolved only once by ADR-0049).
- A future Milestone 3 could add operator visibility, multi-level plans, or richer per-step statuses; none is committed to by this ADR.
