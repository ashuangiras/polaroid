# 0049. `/mcp/agent` is finalized, not experimental; Milestone E does not migrate the legacy catalog

**Status:** Accepted. Supersedes the "experimental" status given to `/mcp/agent` by [ADR-0043](0043-knowledge-first-agent-mode.md) and kept by [ADR-0048](0048-git-native-agent-interface.md); amends [ADR-0038](0038-stable-releases-and-compatibility.md)'s compatibility policy to include it. Amended by [ADR-0051](0051-agent-mode-discover-kinds.md): `discover`'s `kind` argument and its conditional `task` requirement, under the same v1 guarantee this ADR applies.
**Date:** 2026-10-13

## Context

ADR-0044 through ADR-0048 planned a fifth Git-core milestone, E, to migrate the existing SQLite procedure catalog into Git-native knowledge, with a dry-run planner, operator-approved execution, an authority cutover state machine, and crash-recovery tests for all of it (roadmap: "E — Migration and recovery (planned): a controlled, non-destructive path from the SQLite catalog with audit mapping, recovery and rollback").

Before implementing that, this milestone did the inventory Phase E1 called for: a field-by-field classification of every legacy record against the Git-native schema, grounded in the live installation (21 procedures, 50 versions, 10 bindings — every one of them using `contextual` version policy, not a pin — 301 executions, 13 feedback reports, 2 toil items; 2 keys already published in Git-native knowledge, `deployment.smoke-test` and `go.validate.slug-string`, colliding with none of the 21). That inventory surfaced a real semantic gap at its center: a legacy binding's `contextual` policy selects a version by execution evidence (ADR-0013, ADR-0018), which Git-native has no model for at all — a key simply has one current definition. Migrating necessarily means picking "the latest version" regardless of which version is currently evidence-selected, which can differ from a binding's live resolution in rare cases (the same effect the status log already describes for `dev.change.verify`'s own v2 and v6).

Asked to confirm how to resolve that gap (unspecified scope, version-fidelity, retired procedures, collisions — see the four questions below), the owner instead changed the milestone's premise: the existing SQLite content is not worth preserving ("we will recreate our knowledge from scratch"), so there is nothing to migrate. The owner then redefined "feature complete" for Git-core as dropping `/mcp/agent`'s experimental status — the one thing ADR-0048 explicitly left open ("Not decided here: ... whether `/mcp/agent` is finalized (dropped from 'experimental') — all left to a later milestone (E)") — confirming explicitly that SQLite keeps serving what Git-native has no model for: execution and verification evidence, bindings and their `contextual` policy, feedback reports and resolutions, and toil items, all unchanged and indefinitely.

## Decision

1. **No migration is implemented.** Nothing in the legacy SQLite catalog is read, copied, or referenced by Git-native knowledge. The four decisions Phase E1 would have needed (unspecified-scope procedures, version-fidelity, retired procedures, and key collisions) are moot: none is made, because no migration code exists to need them. A later milestone may revisit this if the owner decides old procedural content is worth carrying forward after all; this ADR does not rule that out, it only records that it is not done now.
2. **`/mcp/agent` is finalized under [ADR-0038](0038-stable-releases-and-compatibility.md)'s v1 compatibility guarantee, the same as `/mcp`.** Its three tools (`discover`, `read`, `feedback`), their arguments, required fields and result shapes do not change without the same stability commitment `/mcp` already has. `docs/architecture/mcp.md` drops the "Experimental" framing.
3. **A reviewed, pinned contract for agent mode**, mirroring `/mcp`'s own (`internal/transport/mcp/testdata/agent-mode-tools.json`), checked by `TestAgentModeToolContract` (served schema vs. the reviewed contract) and `TestAgentModeContractIsDocumented` (the contract vs. `mcp.md`'s own tools table) — the same two-sided guard `/mcp` has had since ADR-0038, so a future change to agent mode's arguments or result shape fails a test, not just a review. `TestFullModeToolContract` and `TestFullModeContractIsDocumented` are unchanged in behavior; their shared machinery is factored into `toolsOf`, `checkToolContract` and `checkContractDocumented` so both modes use the same checks.
4. **No other behavior changes.** Agent mode's discover/read/feedback semantics, its Git-native backing (ADR-0045–0048), and `internal/knowledgeops`/`internal/transport/httpops`'s operator surface are exactly as ADR-0048 left them. SQLite (`internal/memory`), the full `/mcp` API, and its 40-tool contract are untouched.

## Consequences

- ADR-0038's Status line now also names this ADR; ADR-0043's and ADR-0048's Status lines are updated to say `/mcp/agent` is no longer experimental, finalized here — their Decision and Consequences text is otherwise unchanged (an accepted ADR's substance is never edited, per the decisions index).
- The roadmap's Git-core item E is complete, redefined: finalizing `/mcp/agent`, not migrating SQLite. There is no further milestone F planned for Git-core; any future migration work is a new, separately-scoped item.
- Everything Phase E1 found SQLite-only (bindings and `contextual` resolution, executions and verification, feedback and its resolutions, toil items, catalog statistics, write limits) stays exactly where it is, serving `/mcp` exactly as before. This is not a stopgap: it is now the acknowledged, permanent division of responsibility between the two stores — SQLite proves work happened and was verified; Git-native knowledge holds the current shared instructions.
- An agent or operator relying on `/mcp/agent`'s current arguments and result shapes may now do so under the same stability expectations as `/mcp`.
