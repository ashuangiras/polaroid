# 0058. Guided Procedures M6: reasoned walkthrough steps

**Status:** Accepted (Milestone 6 of the initiative [ADR-0052](0052-ordered-sibling-steps.md) opened; amends [ADR-0053](0053-guided-walkthroughs.md)'s `start`/`advance` result, additively, the same way ADR-0054 through ADR-0056 already did. Depends on [ADR-0057](0057-typed-record-completeness.md)'s completeness bar, activated by #164, without which this milestone would resolve against empty obligations).
**Date:** 2026-10-17

## Context

`start` and `advance` ([ADR-0053](0053-guided-walkthroughs.md)) track a walkthrough's *position* — which composed child is `next`, and what an agent has reported for each — by calling `reasoning.PlanTree`, deliberately not the full `reasoning.Resolve`: `internal/knowledgeops/guide.go`'s own doc comment says why, "a walkthrough's context is only captured here, not yet reasoned over." `context` is accepted on both calls and folded into `WalkthroughState` ([internal/memory/walkthrough.go](../../../internal/memory/walkthrough.go)), but nothing downstream ever reads it back. An agent working a walkthrough today gets *where* to go next with no formal account of *what that step actually obligates* — it has to make a second, separate, stateless `resolve` call itself, restating the goal and resending every fact of context it has accumulated, to get that — which is exactly the per-turn restatement cost this whole initiative exists to remove (ADR-0053's own opening: "an agent whose own context is gone has no `completed` list to resend").

This was the right call when ADR-0053 through ADR-0056 were written: [ADR-0057](0057-typed-record-completeness.md) records that the live corpus, at the time, had no `definition` and no formal `requires`/`preconditions`/`postconditions` on its typed records, so "`resolve`'s `plan` has nothing to evaluate and a walkthrough is empty motion." #164 cleared that backlog and activated the completeness gate; `discover(kind="stats")` against the live corpus now reads `missing_definition: 0, missing_obligation: 0` across all 31 procedures. The blocker this milestone depended on is gone.

## Decision

**Resolve exactly one leaf per call: the plan's own `next`.** On `start` and on every `advance` (including a no-`outcome` peek), after `plan`/`status` are derived exactly as ADR-0053–0056 already define, if `next` names a leaf (a bare key, or the last element of a multi-level `path`, ADR-0054), that leaf's key becomes `req.Goal` for one `reasoning.Resolve` call against the walkthrough's own pinned snapshot. Nothing is resolved for a `done`, `skipped` or not-yet-reached leaf, and nothing is resolved once `status` is `"complete"` (no `next` remains) — the same way ADR-0055 added no special-cased cleanup for completion, this adds no special-cased resolution for it either. This keeps cost constant and bounded regardless of plan size or depth: unlike `expand` (ADR-0056), whose cost scales with the whole tree and is therefore opt-in, resolving one leaf costs exactly one ordinary `resolve` call, already bounded by `ResolveTimeout` and `Limits` ([internal/knowledgeops/resolve.go](../../../internal/knowledgeops/resolve.go)) — so it is **not** opt-in; it is the default, because the entire point of this milestone is that an agent gets the reasoned account of its actual next step without having to know to ask for it.

**A new, additive response member, `resolution`**, on `start` and `advance`'s result, alongside the existing `token`/`snapshot`/`plan`/`status` ([`wire.WalkthroughResult`](../../../internal/transport/wire/walkthrough.go)): the same shape `resolve` already returns (`wire.KnowledgeResolution`) — `obligations`, `specializations`, `derived`, `exceptions`, `conflicts`, `unknowns`, `evidence`, `complete`/`incomplete` — scoped to the one `next` leaf, not the walkthrough's own root goal (already seen once, at `start`). Named `resolution`, not reusing any of `plan`'s field names, the same collision-avoidance ADR-0055 used choosing `status` over `resolve`'s own `complete`/`incomplete`. Omitted entirely (`omitzero`) when there is no `next` to resolve, matching how `plan` itself is already omitted when a goal has no composed children.

**Context keeps accumulating exactly as ADR-0053 already defined; trust does not.** The free-form `context` folded across a walkthrough's events (ADR-0053's per-key fold) is what is passed as this call's `Resolve` `Context` — so a fact given at `start` still applies when its leaf is reached several `advance` calls later, which is the actual gap this milestone closes. Verified trust is different: `start`/`advance` gain the same `assertions` argument `resolve` already has, established via `policy.Establish` at **that call's own time**, never persisted or inherited from an earlier call in the same walkthrough — avoiding the harder question of whether an assertion presented on day one should still count three days into an open walkthrough by simply never storing it, the same "checked when it is presented, never backdated" rule `resolve` already applies to its own `assertions`. This requires `Guide` ([internal/knowledgeops/guide.go](../../../internal/knowledgeops/guide.go)) to be constructed with a `reasoning.Evaluator` and a `policy.Trust`, exactly as `Resolver` already is ([internal/knowledgeops/resolve.go](../../../internal/knowledgeops/resolve.go)); `cmd/polaroidd` passes the same two already-constructed instances to both, no new material and no new `internal/archtest` boundary (`internal/knowledgeops` already imports `internal/reasoning` and `internal/reasoning/policy` through `Resolver`).

**No retroactivity, by construction, not by special-casing.** Because resolution is computed only for `next`, the question "does new context change what an already-`done` leaf's obligations looked like" never arises: Polaroid never re-derives anything for a leaf once it has left `next`. A leaf resolved once as `next`, then marked `done`, is never resolved again even if later context would have changed its answer — the walkthrough's historical `resolution` members (had the caller kept them) are the only record of what applied at the time, the same "no retroactive rewrite" stance the rest of this catalog already takes toward immutable history.

**`resolution`'s `unknowns`/`exceptions`/`conflicts` are informational, never status-deciding.** They do not set, freeze or clear `next`'s `escalate`/`blocked` the way an agent's own reported outcome does (ADR-0053, ADR-0056); Corpus Logic remains open-world and still cannot derive that a step is blocked ([ADR-0056](0056-walkthrough-visibility-and-status.md)). An agent now simply has the formal basis in front of it — unresolved obligations, an open exception, a conflict — to decide, on its own judgment, whether to report `escalate` or `blocked`, instead of needing a second round trip to `resolve` to find that basis itself. A leaf whose goal carries no obligations at all is not an error; `resolution` just carries empty `obligations`/`unknowns`, the same as calling `resolve` on any such goal today.

**Budget.** `start`/`advance` now carry the same `ResolveTimeout`/`Limits` a bare `resolve` call already risks exceeding; `budget_exceeded` becomes a possible error from `start`/`advance` for the first time, handled the same way `resolve` already handles it. A repeated `budget_exceeded` on the same leaf is not retried or backed off specially — the caller sees it again next call, exactly as `resolve` already behaves, until its own context or trust changes.

**Explicitly not decided here:**
- Extending `expand`'s nested `children` (ADR-0056) with their own `resolution` per node — left for if usage shows it is wanted; this milestone resolves only the top-level `next`, never a deeper, not-yet-reached node.
- Any change to the stateless `resolve` tool itself, or to `reasoning.Plan`/`PlanTree`'s own signatures.
- Any caching or reuse of a `resolution` already computed for the same leaf and context on an earlier call — each call resolves fresh, the same as `resolve` already does on every call.

## Consequences

- `start`/`advance` become genuinely reasoned: an agent sees, in the same call that tells it what's next, exactly what that step obligates given everything it has told Polaroid so far — closing the gap ADR-0057 was written to eventually enable, without which this would have resolved against empty obligations.
- `Guide` depends on `reasoning.Evaluator` and `policy.Trust`, the same two dependencies `Resolver` already carries; `cmd/polaroidd`'s wiring shares both instances, adding no new package or boundary exception.
- `start`/`advance`'s result gains one new optional member (`resolution`) and gains the existing `assertions` argument; a caller using neither sees no change to `token`/`snapshot`/`plan`/`status`, the same additive pattern every prior milestone in this initiative has used.
- Latency and failure modes: a walkthrough call now costs one bounded `resolve` pass in addition to the existing plan traversal, and can now fail `budget_exceeded`, a case `start`/`advance` could not previously reach.
