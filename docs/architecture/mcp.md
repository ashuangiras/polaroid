# MCP server

`polaroidd` serves the [Model Context Protocol](https://modelcontextprotocol.io) at **`/mcp`**, beside the [HTTP API](http-api.md) and on the same listener. The default URL is `http://127.0.0.1:7417/mcp`. It exposes the same operations as tools and resources. Decisions are in [ADR-0014](decisions/0014-mcp-transport.md).

## Transport

- **Protocol:** streamable HTTP, revisions **2026-07-28** and **2025-11-25** ([ADR-0016](decisions/0016-mcp-protocol-2025-11-25.md)). 2026-07-28 is sessionless by design. A 2025-11-25 client begins with the `initialize` handshake, but it gets no session either: each POST is a complete request at both revisions, with identical tools, results and errors.
- **Older clients:** a request naming an older revision is refused with `400 Unsupported protocol version`. An older `initialize` is answered with 2025-11-25, and a client that cannot speak it disconnects.
- **Responses:** JSON (`application/json`), never SSE. There is no `Mcp-Session-Id`, and `GET` and `DELETE` are not used.
- **Limits and security:** bodies are limited to 1 MiB. `/mcp` sits behind the same loopback `Host` check and cross-origin protection as the API, with no authentication ([ADR-0006](decisions/0006-local-unauthenticated-api.md)).
- **Caching:** every `server/discover`, list and `resources/read` result carries `ttlMs: 0`, the protocol's cache hint (SEP-2549) for "immediately stale". The tools change when `polaroidd` is upgraded and records change with every write, so a client must not answer from a cached result. `serverInfo.version` is informational and stays `v1`; it does not change with the tool catalogue.
- **Server capabilities:** `tools` and `resources`, plus short instructions that describe the agent loop. They tell agents to find their repository's bindings and the procedures that may fit their task (`discover_procedures` with the task and `repository`: lexical matches with explanations, latest versions only, relevance judged by the agent; `list_procedures` with `repository` for everything that applies there; a listed scope is the latest version's, and unspecified declares nothing), that evidence under any identifier of a registered repository counts for all of them ([ADR-0022](decisions/0022-repository-identity-in-evidence.md)), that every graph node names its version's own scope, to be read with that version's contract before reuse, that `selection_evidence` explains why a version was selected and does not verify their checkout, that `commit` and `inputs` give `target_verification` for the exact run, and that an unverified target still has to be run and recorded ([ADR-0018](decisions/0018-selection-evidence-and-target-verification.md)). Children are recorded first, each with the inputs its reference maps from the parent's ([ADR-0024](decisions/0024-child-inputs-follow-the-reference-mapping.md)). A reference with a condition applies only when it holds: agents decide each one themselves, record a decision for each, and pass their decisions for target verification ([ADR-0029](decisions/0029-conditional-references-and-applicability-decisions.md)). Lists continue with the same arguments, and the procedure, binding and toil item lists can page a snapshot ([ADR-0023](decisions/0023-pagination-guarantees-and-scope-labels.md)). New procedures declare applicability and origin, and agents check a proposal with `suggest_duplicates` before creating or revising one, preferring to reuse or revise an overlapping procedure ([ADR-0032](decisions/0032-lexical-discovery-and-duplicate-suggestions.md)). The last step asks agents to check `list_feedback` with `status` `open` first, then report problems with Polaroid, and suggestions for it, with `report_feedback`, naming the subject, and to resolve a report they addressed with `resolve_feedback` ([ADR-0015](decisions/0015-feedback-reports.md), [ADR-0021](decisions/0021-targeted-feedback-and-bounded-lists.md), [ADR-0040](decisions/0040-feedback-resolution.md)). A final step asks agents who see repetitive, mechanical work to look for an existing toil item with `list_toil_items` before creating one, to revise it when they observe the activity again, to cite exact versions and executions, to keep observed facts apart from hypotheses, and to treat its status as their assessment, not verification ([ADR-0034](decisions/0034-toil-items.md)).

## Tools

Arguments are flat JSON objects, named after the record fields in [records.md](records.md).

- **Decoding is strict, as for HTTP request bodies.** Unknown or duplicate members are rejected, and so are values of the wrong JSON type. Free-form objects (`contract`, `instructions`, `inputs`, `evidence`, `environment.attributes`, reference `inputs`, feedback `context`, toil `assessment` and `proposal`) are stored with their member order intact, as Polaroid receives it. MCP clients may reorder members before sending (VS Code Copilot chat does), so keep order-sensitive data in arrays ([records.md](records.md#procedure-version-implemented)).
- **Schemas:** every tool advertises an input schema generated from its argument type.
- **Contract:** this table, and the argument names, JSON types, nesting and requiredness in [`internal/transport/mcp/testdata/full-mode-tools.json`](../../internal/transport/mcp/testdata/full-mode-tools.json), are the v1 contract of `/mcp` ([ADR-0038](decisions/0038-stable-releases-and-compatibility.md)). Tests compare the served schemas with that file, and that file with this table, so any change to a tool's arguments must be made deliberately in both.

There are 42 tools: 27 read-only, and 15 that only append. The repository, scope and paging rules are those of the HTTP API ([ADR-0019](decisions/0019-repository-registry.md), [ADR-0020](decisions/0020-procedure-origin-and-applicability.md), [ADR-0021](decisions/0021-targeted-feedback-and-bounded-lists.md)); discovery and duplicate suggestions are lexical and store nothing ([ADR-0032](decisions/0032-lexical-discovery-and-duplicate-suggestions.md)); toil items follow [the HTTP rules](http-api.md#toil-items) ([ADR-0034](decisions/0034-toil-items.md)); invalidation and retirement follow [ADR-0035](decisions/0035-evidence-invalidation-and-procedure-retirement.md): an invalidation is permanent and changes no record, and a retirement is reversed only by a reactivation. `get_catalog_statistics` returns the document of `GET /v1/statistics` and stores nothing ([ADR-0036](decisions/0036-read-only-catalog-statistics.md)); any argument is `invalid_request`. Every write tool applies the HTTP API's [write limits](http-api.md#write-limits) ([ADR-0037](decisions/0037-size-limits-on-new-writes.md)): a value over its limit is a `value_too_large` tool error whose `limits` name the flat argument (`contract`, not `version.contract`), its size and its limit; `get_catalog_statistics` lists the limits under `write_limits`, with the HTTP field paths. `list_walkthroughs` and `get_walkthrough` give an operator read-only visibility into the guided-procedure walkthroughs agents run through `/mcp/agent/v3`'s `start` and `advance` ([ADR-0056](decisions/0056-walkthrough-visibility-and-status.md)): a walkthrough document has `token`, `goal`, `snapshot`, `repository` (omitted when not given), `context` (always present, `{}` when none was given), `status`, `created_at`, `expires_at` and `leaves` (each `{key, status, reason, note}`, `reason` and `note` omitted when not given). `status` here is coarser than `start`/`advance`'s own `in_progress`/`complete`: this surface has no access to the composition tree that those derive from (the same `internal/archtest` boundary every other milestone of this initiative kept), so it can only report `active` (nothing currently stuck — which also covers an already fully done walkthrough, indistinguishable at this layer), `escalate` or `blocked`. `leaves`' `key` is the raw string a walkthrough's outcome was stored under, opaque to this surface: for a multi-level outcome ([ADR-0054](decisions/0054-multi-level-plans.md)) it is the full path joined with `/`. An unknown or expired token is `not_found`, the same as on `/mcp/agent/v3`; listing or getting a walkthrough never resets its TTL the way `advance` does.


### Results

A successful result carries the record exactly as the HTTP API returns it ([http-api.md](http-api.md)), in two places:

- as structured content;
- as one text item holding the same JSON, with the server's member order.

### Errors

A failed call is a tool error (`isError: true`). It carries the HTTP API's error body, `{"error":{"code","message",…}}`, as text and as structured content, with the same codes: `invalid_request`, `not_found`, `version_conflict` (with `latest_version`), `revision_conflict` (with `latest_revision`), `canonical_key_exists`, `binding_exists`, `repository_identifier_exists`, `origin_exists`, `reference_cycle` (with `cycle`), `graph_too_large`, `execution_invalidated`, `lifecycle_conflict` (with `latest_event`), `lifecycle_unchanged`, `procedure_retired`, `value_too_large` (with `limits`) and `internal`.

Field names in `fields` are the flat argument names. For example, a missing `philosophy` is reported as `philosophy`, not `version.philosophy`, and a reference to a retired procedure as `references[0].procedure_id`. A reference is still reported as `references[i]…`. An unexpected failure is logged, and only `internal` is returned.

## Agent mode (`/mcp/agent`)

See [knowledge-guide.md](knowledge-guide.md) for a practical, worked-example guide to using agent mode in a repository (setup, discover/read/resolve/feedback, storing knowledge); this section and the next are its normative tool contract.

**Finalized, under the v1 compatibility guarantee** ([ADR-0038](decisions/0038-stable-releases-and-compatibility.md), amended by [ADR-0043](decisions/0043-knowledge-first-agent-mode.md), built on Git-native living knowledge by [ADR-0048](decisions/0048-git-native-agent-interface.md), finalized by [ADR-0049](decisions/0049-agent-mode-finalized-no-migration.md), `discover`'s `kind` argument added by [ADR-0051](decisions/0051-agent-mode-discover-kinds.md)): the same stability promise as `/mcp` applies to its three tools, their arguments and their result shapes.

A second endpoint on the same listener, with the same transport rules, serves only the three tools everyday procedural-knowledge use needs ([ADR-0043](decisions/0043-knowledge-first-agent-mode.md)). A client connected to it never loads the full API's schemas, and nothing it does records an execution. It is backed solely by living knowledge in a separate, Git-native store ([ADR-0045](decisions/0045-living-knowledge-kernel.md)), named only by canonical key and an opaque snapshot token: there is no procedure version, binding, or evidence-based selection anywhere in this mode, and it shares no record with `/mcp`'s procedures, versions, bindings, executions or verifications.

| Tool | Read-only | Arguments | Result |
| --- | --- | --- | --- |
| `discover` | yes | `kind` (`procedures`, the default, `stats` or `tools`), optional; `task` (required only for `kind=procedures`); `repository` and `limit` (1 to 50, default 5), optional, only for `kind=procedures`; `snapshot`, optional, only for `kind=stats` | **`kind=procedures`:** `{"snapshot", "candidates":[{key, goal, score}]}`, best first; `{"empty": true, "message"}` when nothing has been published or activated yet (a normal result, not an error). **`kind=stats`** ([ADR-0051](decisions/0051-agent-mode-discover-kinds.md)): `{"snapshot", "kind", "generated_at", "by_type", "by_domain", "procedures": {"total", "by_repository"}, "completeness": {"missing_definition", "missing_obligation"}}`, counts over the snapshot (the active one, or `snapshot`). **`kind=tools`:** `{"kind", "tools": [{name, description, read_only}]}`, this endpoint's own tools |
| `read` | yes | `key`; `snapshot` (default: the active knowledge), `repository` (checked against applicability), `inputs` (an object) and `full` optional | guidance: `snapshot`, `key`, `scope`, `goal`, `method`, `contract`, `instructions`, `references` `[{name, key, goal, condition, inputs or input_mapping}]`, resolved only one level (read a reference's own `key` for its references); with `full`, also `philosophy` |
| `feedback` | no | `key`, `snapshot` (the one `read` or `discover` gave), `classification`, `summary`, `reporter`; `details`, `repository` and `evidence` (an object) optional | `{id, classification, created_at}`; the stored report is an ordinary [feedback report](http-api.md#feedback), with no subject, whose `context` carries `{classification, evidence}` and, under a reserved `knowledge` member, `{key, snapshot}` |

- **Snapshots pin knowledge.** A snapshot token from `discover` or an earlier `read` always reads exactly that published state, however much is published or activated later; omit it to read the active knowledge.
- **`discover(kind="stats")`** ([ADR-0051](decisions/0051-agent-mode-discover-kinds.md)): `by_type` counts every typed Corpus Logic record ([ADR-0050](decisions/0050-corpus-logic.md)) by its record type (`Domain`, `Concept`, `Claim`, `Rule`, `Procedure`, `Evidence`, `Exception`), every type listed, zero included. `by_type["Procedure"]` is the typed reasoning record count, not the same as `procedures.total`: every typed `Procedure` record names a published procedure, but not every procedure has one yet. `by_domain` groups typed records by the `Domain` record(s) they are directly `classified_as` (not transitively through `broader`); a record with none counts under `"unclassified"`. `procedures.total` and `procedures.by_repository` count the procedure documents `discover(kind="procedures")` and `read` serve, by applicability: `"shared"`, `"unspecified"` (no declared applicability), or the repository identifier of a locally scoped one. With `repository`, only `procedures` is limited to what applies there; `by_type` and `by_domain` carry no per-repository applicability and are never filtered. `limit` is rejected with `kind=stats` or `kind=tools`.
- **`completeness`** ([ADR-0057](decisions/0057-typed-record-completeness.md)): `missing_definition` counts `Domain`, `Concept` and `Procedure` records with an empty `definition`; `missing_obligation` counts `Procedure` records with none of `requires`, `preconditions` or `postconditions`, own or inherited transitively via `specializes`. Informational only: nothing is refused for either today, and `completeness` carries no per-repository applicability (typed records have none), so it is never scoped by `repository`.
- `feedback` classifications: `incorrect_applicability`, `missing_precondition`, `incorrect_instruction`, `inadequate_verification` (kind `problem`) and `improved_method` (kind `suggestion`). `product_defect`, `environment_problem` and `transient_failure` are `invalid_request`: they are not procedural knowledge. Before recording, the daemon confirms the pair is real: a snapshot that never served `key`, or a key never published, is `not_found`.
- A read with `repository` set and the procedure's applicability local to another repository is `not_applicable`.
- Errors use the same envelope as the full API's tool errors, with these codes: `invalid_request`, `not_found`, `not_applicable`.
- **Publishing, synchronising and reconciling knowledge is an explicit operator operation**, through `/v1/knowledge/*` ([http-api.md](http-api.md#git-native-knowledge-operator-api)) or `polaroid knowledge-*`, never through agent mode: there is no scheduler, and an agent only discovers, reads and reports feedback.
- **Migrating an agent:** point it at `http://127.0.0.1:7417/mcp/agent` instead of `/mcp`. Keep `/mcp` for administration, execution and verification records, and audit workflows; its 42 tools are unchanged. No legacy SQLite procedure is migrated into Git-native knowledge ([ADR-0049](decisions/0049-agent-mode-finalized-no-migration.md)): the two catalogs are populated independently.

## Agent mode v2 (`/mcp/agent/v2`)

**Implemented with Corpus Logic v1** ([ADR-0050](decisions/0050-corpus-logic.md), merged as PR #143). This is a separate, versioned endpoint; `/mcp/agent` above is unchanged.

It serves the same `discover`, `read` and `feedback` tools, with input schemas identical to v1's (a test compares them), plus one read-only tool:

| Tool | Read-only | Arguments | Result |
| --- | --- | --- | --- |
| `resolve` | yes | `goal` (a record key: a procedure, concept or claim); `snapshot` (default: the active knowledge), `context` (an object of string name and value pairs), `assertions` (signed context assertions, below), `then` (a procedure key to compose after the goal), `completed` (keys of `goal`'s immediate composed children already considered done, [ADR-0052](decisions/0052-ordered-sibling-steps.md)) and `at` (RFC 3339; default now) optional | `{version, snapshot, goal, at, trusted, complete, incomplete, applicable, specializations, obligations, derived, exceptions, conflicts, unknowns, evidence, superseded, composition, plan}` |

The result members mean:

- **`complete`**: whether every conclusion the missing context could add was examined. When it is false, **`incomplete`** says what could not be enumerated: a rule that reads a context name or value it does not fix, or more than 64 combinations of missing values. Unknowns are then not exhaustive.
- **`obligations`**: each requirement with every independent derivation `{id, source, source_type, via, path, status, exception}`. The status is `required` while any derivation is active, otherwise `waived`.
- **`exceptions`**: each exception that concerns the goal, with its status: `applied`, `rejected`, `not_applicable` or `conflicting`, and a reason.
- **`conflicts`**: requirements that contradict each other, conflicting exceptions, and `undefined_requirement` for a derived requirement that is not a concept.
- **`unknowns`**: each conclusion that holds only for context the caller did not give, `{kind, requirement or predicate and object, source, when, reason}`. `kind` is `obligation` or `derived`; `when` lists the `{name, value}` pairs it needs.
- **`evidence`**: each claim's evidence status (`supported`, `contradicted`, `contested`, `unsupported`). It summarises the evidence and is never a verdict.
- **`superseded`**: rule keys that would have contributed an obligation or derived fact to this goal, but are superseded in this snapshot ([ADR-0050](decisions/0050-corpus-logic.md)). A superseded rule's program still evaluates, but its rows never reach `obligations`, `derived` or `applicable`; it is reported here instead.
- **`composition`**, with `then`: `{verdict, producer, consumer, findings}`. The verdict is `compatible`, `incompatible` or `undetermined`; `producer` and `consumer` are the two formal contracts (inputs, outputs, whether the outputs are complete, pre-, post-conditions, invariants, informal conditions); each finding covers one consumer input, precondition or informal condition, and those not `satisfied` or `established` are the missing prerequisites. Composition reads only the snapshot, never `context`.
- **`plan`** ([ADR-0052](decisions/0052-ordered-sibling-steps.md)), present only when `goal` `composes`: its immediate composed children, one level (a composed child that is itself composed is resolved separately, exactly as `read`'s references resolve only one level), topologically ordered by their `precedes` relation (ties broken by key), each `{key, status}` — `status` is `done` for a key named in `completed`, `next` for the first not-done one, or absent for the rest. A `completed` key that is not one of `goal`'s immediate composed children is `invalid_request`. Fully stateless: the same `completed` on the same snapshot always gives the same `plan`.

`context` is what the caller asserts. It selects which rules apply, but never authorises an exception. Project-scoped exceptions and exception conditions need trusted context, which comes only from `assertions`: signed context assertions the caller was given, for example by its CI, each `{reference, key, repository, facts, valid_from, valid_until, signature}` with a base64 Ed25519 signature ([ADR-0050](decisions/0050-corpus-logic.md)). An assertion that is not signed by a trusted attestation key for its repository, that asserts a name the key may not assert, that is not valid both at `at` and at the server's current time, whose validity times are not whole seconds, or that disagrees with another assertion, fails the request with `invalid_request`, and so do more than 16 assertions and a `context` value that contradicts a trusted fact. The result's `trusted` is the trusted context used. An exception approval's own validity is judged at `at`, so a resolution at an earlier time reports what applied then; revocations always apply. Without assertions, project-scoped and conditional exceptions are reported `not_applicable`, with a reason that says when the caller asserted a matching value. A domain exception applies only while the domain path its approval signed still holds in the snapshot. Protected invariants are never waived, at any authority.

Resolution is deterministic. The same snapshot, `context`, `assertions`, `at` and trust material give byte-identical results. A derivation `id` is the first 16 bytes, in hex, of SHA-256 over the reasoning version, the snapshot, the goal and the derivation's parts, joined by NUL bytes ([ADR-0050](decisions/0050-corpus-logic.md)); anyone holding the snapshot can recompute it. It identifies the derivation, not its status.

Requests can fail with these codes:

- `not_found`: the goal is not a record of the snapshot or, with `then`, the goal or `then` is not a procedure of it.
- `invalid_request`.
- `budget_exceeded` (HTTP 422): the evaluation exceeded its time or fact limits. A budget failure never returns a partial result.

Exceptions and assertions are verified against the operator-held trust material at `<knowledge-dir>-authorities.json` ([http-api.md](http-api.md#git-native-knowledge-operator-api)).

## Agent mode v3 (`/mcp/agent/v3`)

**Implemented by [ADR-0053](decisions/0053-guided-walkthroughs.md) (Guided Procedures, Milestone 2), amended for multi-level plans by [ADR-0054](decisions/0054-multi-level-plans.md) (Milestone 3), for completion semantics and an early close by [ADR-0055](decisions/0055-walkthrough-completion.md) (Milestone 4), for a blocked status, operator visibility and an expand option by [ADR-0056](decisions/0056-walkthrough-visibility-and-status.md) (Milestone 5), and for reasoned steps by [ADR-0058](decisions/0058-reasoned-walkthrough-steps.md) (Milestone 6).** This is a separate, versioned endpoint; `/mcp/agent` and `/mcp/agent/v2` above are unchanged. Not yet finalized: the same "experimental until explicitly finalized" path `/mcp/agent` itself took before [ADR-0049](decisions/0049-agent-mode-finalized-no-migration.md).

It serves the same `discover`, `read`, `feedback` and `resolve` tools, with input schemas identical to v2's (a test compares them), plus two new, non-destructive write tools: Polaroid's first stateful agent-mode capability.

| Tool | Read-only | Arguments | Result |
| --- | --- | --- | --- |
| `start` | no | `goal` (a record key: a procedure, concept or claim); `repository` and `context` (an object of string name and value pairs), optional, stored with the walkthrough but not checked against anything; `expand` (boolean), optional — return the whole nested plan tree instead of discovering depth one leaf at a time; `assertions` (an array, resolve's own shape), optional — establishes trusted context for this call's own resolution alone, never stored or inherited by a later call | `{token, snapshot, plan, status, resolution}`: a new walkthrough, with nothing reported yet. `resolution` (ADR-0058) is resolve's own result shape, scoped to `plan`'s current `next` leaf, resolved fresh against the walkthrough's pinned snapshot and its accumulated `context`; omitted once `status` is `"complete"` |
| `advance` | no | `token`; `outcome` (`{key or path, status: "done"\|"skipped"\|"escalate"\|"blocked", reason, note}`), optional — without it, a pure peek; `context` (an object), optional, added to what this walkthrough has reported so far; `close` (boolean), optional — ends the walkthrough immediately, after `outcome` (if given) is applied; `expand` (boolean), optional, as `start`'s; `assertions` (an array), optional, the same call-scoped meaning as `start`'s | `{token, snapshot, plan, status, resolution}`: the updated walkthrough, `resolution` as `start`'s |

- **`start` resolves `goal` at the active snapshot and pins it** for the new walkthrough's lifetime, the same guarantee `discover`'s and `read`'s snapshot tokens already give: later publications or activations never change an existing walkthrough's `plan`. A `goal` without composed children is not an error: it starts with an empty, trivially complete `plan`. A `goal` that is not a record of the active snapshot is `not_found`; unlike `read`'s legacy procedure documents, a typed record has no applicability to check, so there is no `not_applicable` case here.
- **`plan`'s top level is always exactly `goal`'s immediate composed children**, one entry each, in `precedes` order ([ADR-0052](decisions/0052-ordered-sibling-steps.md)): `{key, status, path}`. `status` is `"done"` (every leaf beneath it is done or skipped), `"next"` (the first not-done entry), `"escalate"` or `"blocked"` (a leaf beneath it is frozen there), or absent (the rest, not yet reached). **A composed entry's status is always derived from its own descendants, never directly reported** ([ADR-0054](decisions/0054-multi-level-plans.md)): an agent never calls `advance` for a composed key, only for leaves. `path`, present only on the `"next"`, `"escalate"` or `"blocked"` entry, is the full chain of keys from that entry down to the actual leaf to act on or that is stuck — a single-element array, equal to `[key]`, when that entry is itself a leaf (the common case, and the only case before Milestone 3).
- **`advance`'s outcome accepts `key` (shorthand for a one-element `path`) or an explicit `path`**, for a leaf found several levels down; exactly one of them is required. Either way, the named key must be an actual leaf — reached from `goal` by following `composes` at every level — never a composed node, whose status is always derived; a key or path that does not resolve to a real leaf this way is `invalid_request`.
- **`status` is `"done"`, `"skipped"`, `"escalate"` or `"blocked"`** ([ADR-0056](decisions/0056-walkthrough-visibility-and-status.md)). `escalate` and `blocked` both freeze `plan`'s `next` on that leaf until a later `advance` reports `done` or `skipped` for it, and are reported distinctly, never merged: `escalate` means waiting on a person's judgment; `blocked` means an external, technical precondition is not met — never Polaroid's own conclusion, always the agent's own testimony (Corpus Logic is open-world and cannot derive blocking itself). `reason` is optional free text specific to a `blocked` report, for example a missing required tool; nothing refuses it alongside another status. `note` remains available for any status, as before.
- **`advance` folds per leaf, not "latest wins".** For each leaf (addressed by its full path), its current status is whichever outcome was *last* reported for that specific path: a later `done` overrides an earlier `escalate` or `blocked` for the same leaf; reporting the same status again is harmless. The same sub-procedure key reused in two branches of one plan is two distinct leaves, addressed and folded independently by their distinct paths; completing one never affects the other. Leaves never reported stay pending.
- **`escalate` or `blocked` freezes `plan`'s `next` on that leaf, however deep it is**, and every composed ancestor above it also reports the same status, visible at the top level without the agent needing to already know the path; `blocked` takes priority over `escalate` when an ancestor's descendants include both. Nothing else ever clears it; there is no time-out or auto-resolution, TTL expiry aside.
- **`status`** ([ADR-0055](decisions/0055-walkthrough-completion.md)), on both `start` and `advance`: `"complete"` exactly when `plan` has no entry left `"next"`, `"escalate"` or `"blocked"` (equivalently, every entry is `"done"`, or `plan` is empty), `"in_progress"` otherwise. Deliberately not named `complete`/`incomplete`, to avoid colliding with `resolve`'s own, differently-meant pair on the same endpoint family (reasoning completeness, not task completeness). **Not terminal**: because `status` is derived from the same per-leaf fold `advance` always uses, a later `advance` correcting an already-done leaf (back to `escalate` or `blocked`, for example) moves `status` back to `"in_progress"` — no new state machine, nothing extra computed. A `"complete"` walkthrough is not deleted or treated differently by the TTL; it keeps sliding exactly like any other until it expires or is closed.
- **`expand`** ([ADR-0056](decisions/0056-walkthrough-visibility-and-status.md)), on both `start` and `advance`: `true` attaches `children` (recursively) to every composed entry, so the whole nested plan tree is visible in one call instead of discovering it depth one leaf at a time via `path`. **The top level is byte-identical to the non-`expand` plan** — same `next`/`path`/`escalate`/`blocked` semantics, strictly positional (only the first not-done sibling is ever `"next"`). A nested `children` entry's own status is `"done"`, `"escalate"`, `"blocked"` or `"pending"` (nothing reported for it or its descendants) instead, computed independently of its siblings' order: an expanded view can show several blocked or escalated leaves at once, in any position, which is a deliberate divergence from the top level's strict positional semantics — `expand`'s whole purpose is seeing the real state of everything at once, not discovering it one leaf at a time.
- **`close`** ([ADR-0055](decisions/0055-walkthrough-completion.md)): when `true`, ends the walkthrough immediately, whether or not every leaf is done — an explicit abandon, not only a completion shortcut. `outcome` may still be given in the same call: it is applied and reflected in that call's own `{token, snapshot, plan, status}` first, and only then is the walkthrough closed. From that point on the token behaves exactly like an expired one: `not_found` on every later call, no trace kept. `close` on an already-closed or already-expired token is `not_found`, the same as any other operation on one. The TTL remains the only *required* cleanup path; `close` is a courtesy for the common case, never something a caller must remember.
- **Expiry is real and sliding.** Every event, including a no-`outcome` peek, resets the token's expiry to now plus a fixed TTL (an implementation detail, not a governed policy). `advance` on an expired or unknown token is `not_found`, indistinguishable from each other: an expired walkthrough is deleted outright as part of answering, and no trace of it is kept. Walkthroughs are the first record in Polaroid that is not kept forever; they are runtime state, not catalog content, and are never counted by `discover(kind="stats")`.
- **Identity.** A token is an opaque UUIDv7, independent of any other walkthrough: there is no lookup by `(repository, goal)` and no uniqueness constraint, so two agents, or two attempts, can work the same procedure concurrently without colliding. Resuming depends entirely on the caller keeping its token; Polaroid offers no other way to find one.
- **No new size or depth limit.** The underlying `composes` graph's cycle-freedom is already checked at publish time; Polaroid applies a practical recursion ceiling of its own when walking it (the same `MaxGraphDepth` (32) the legacy reference graph is bounded by, [ADR-0009](decisions/0009-reference-graph-rules.md)), though — unlike the legacy graph — a `composes` chain's *depth or node count* is not actually bounded at publish time today; see [internal/reasoning](../../internal/reasoning)'s `PlanTree` doc comment. In practice this never matters: no real procedure composition approaches that depth.
- **An operator's read-only visibility** into a walkthrough's own stored state — `list_walkthroughs` and `get_walkthrough`, with a deliberately coarser `active`/`escalate`/`blocked` status this endpoint family's own `in_progress`/`complete` cannot be, by the same architectural boundary — lives on the legacy, non-agent surface, not here: `/v1/walkthroughs` ([http-api.md](http-api.md#guided-procedure-walkthroughs)) and the MCP tools below ([ADR-0056](decisions/0056-walkthrough-visibility-and-status.md)).

Requests can fail with these codes: `not_found` (an unknown `goal`, or an expired, closed or unknown `token`), `invalid_request` (a missing `goal`/`token`, an `outcome` with neither or both of `key`/`path`, a `key`/`path` that does not resolve to an actual leaf of `goal`'s composition, or an `outcome.status` that is not `done`, `skipped`, `escalate` or `blocked`).

## Agent mode v4 (`/mcp/agent/v4`)

**Implemented by [ADR-0059](decisions/0059-grounded-publication.md) Parts 2–3 (Grounded publication, Milestone 2).** This is a separate, versioned endpoint; `/mcp/agent` through `/mcp/agent/v3` above are unchanged. It serves the same `discover`, `read`, `feedback`, `resolve`, `start` and `advance` tools, with input schemas identical to v3's (a test compares them), plus one new tool: agent mode's first write to knowledge content itself. (`start`/`advance` write too, but only one agent's own runtime walkthrough progress, never knowledge content — a different kind of write, kept on its own endpoint, unaffected by this one.) This is a deliberate, narrowly bounded reversal of the stance every prior milestone held, that agent mode never writes knowledge; see ADR-0059's Context for why.

| Tool | Read-only | Arguments | Result |
| --- | --- | --- | --- |
| `propose` | no | Exactly one of `existing_procedure` (`{key, definition?, preconditions?, postconditions?, invariants?, informal_conditions?, citations}`), `new_concept`/`new_claim` (`{key, label, definition or statement, citations}`), or `new_orchestration` (`{key, label, definition, composes, requires?}`); `citations` is `[{source, quote}]`; `proposer` (who proposes this, canonical-key form); `rationale` | `{snapshot, key}`: the new snapshot and the key committed |

- **Three checks, computed by Polaroid alone, before anything commits.** (1) **Citation self-consistency**: every citation's `quote` must appear verbatim in the new prose content being proposed (`definition`/`preconditions`/`postconditions`/`invariants`/`informal_conditions`, or a new Concept's `definition`/Claim's `statement`) — the one check Polaroid can enforce without filesystem access to any consuming repository; it does not prove `source` is accurate against a real file, only that the agent is not inventing content disconnected from what it claims grounds it. `source` is retained permanently in the committed record for later, independent, human audit. (2) **ADR-0057's completeness and the non-vacuous composition gate** ([ADR-0059 Part 1](decisions/0059-grounded-publication.md)), the latter scoped to only the pairs this proposal's own key touches, never the whole catalog — checking the whole catalog would make `propose` unusable for anything, including fixing a pre-existing vacuous pair unrelated to the current proposal, until every other one happened to be fixed first. (3) **A novelty-diff**: the candidate is resolved against every record and every `precedes`-adjacent composition pair, before and after; a proposal that changes no resolution anywhere is refused as redundant. All three are skipped for a bare `definition` change (Corpus Logic never reads `definition` in any `resolve` or composition output at all, so neither check could ever say anything about it) and for `new_orchestration` (asserts no new operational claim: see below).
- **`new_orchestration` is Tier 1** (ADR-0059 Part 3): a wholly new Procedure whose only content is `composes`, in order, over Procedures that **already exist** — no citation needed at all, since reusing already-vetted procedures asserts nothing new to ground. `requires`, if given, names an already-existing Concept (a reference, not new prose, so it needs no citation either), to satisfy ADR-0057's completeness bar, which `composes` alone does not. The matching legacy procedure document (every typed Procedure needs one) is generated automatically: its `instructions.steps` say exactly "Follow `X`." for each composed key, in order, so the prose can never diverge from what the typed record's own `composes` already asserts. It deliberately never adds a `precedes` edge to an existing composed child's own record (that would modify other, unrelated records as a side effect) — propose that separately, per child, through `existing_procedure`.
- **No draft state, no queue, no operator approval.** Passing every applicable check, `propose` commits immediately through the same path `knowledge-publish` uses, and the result is readable via `discover`/`read`/`resolve` in the very next call.
- **Deliberately independent of `feedback`.** A different purpose — `feedback` is an append-only report that never itself changes served knowledge; `propose` commits — with no shared storage or behavior.

Requests can fail with these codes: `invalid_request` (a missing or malformed field, more than one or none of `existing_procedure`/`new_concept`/`new_claim`/`new_orchestration`, a missing or unverifiable citation, a key that does not exist or already exists where the opposite is required, a reference to an unknown or wrong-typed record, a completeness or non-vacuous-composition failure, or a redundant candidate), `not_found` (the active snapshot cannot be read).

## Agent mode v5 (`/mcp/agent/v5`)

**Implemented by [ADR-0060](decisions/0060-interactive-proposal-drafts.md).** This is a separate, versioned endpoint; `/mcp/agent` through `/mcp/agent/v4` above are unchanged. It serves the same `discover`, `read`, `feedback`, `resolve`, `start`, `advance` and `propose` tools, with input schemas identical to v4's (a test compares them), plus two new tools that build an `existing_procedure` `propose` call interactively, field by field, instead of requiring an agent to assemble the whole call itself.

| Tool | Read-only | Arguments | Result |
| --- | --- | --- | --- |
| `propose_start` | no | `{key, proposer, rationale}` | `{token, snapshot, next_field, status}` |
| `propose_advance` | no | `{token, outcome?: {field, values?, citations?, confirmed_absent?, reason?}, close?}` | `{token?, snapshot?, key?, next_field?, status}` |

- **Four content fields, one fixed order.** `preconditions`, `postconditions`, `invariants`, `informal_conditions` — the same fields `existing_procedure` already accepts on `propose`. `propose_start` resolves and pins the key at the active snapshot, then reports the first of these not yet marked complete on the record (its own `*Complete` flag, [ADR-0060](decisions/0060-interactive-proposal-drafts.md)'s generalization of the existing `outputs_complete` precedent) as `next_field`; `status` is `"complete"` immediately, with nothing to answer, only if every field was already decided.
- **Every field needs an explicit answer: real content, or a reasoned decline.** `propose_advance`'s `outcome` gives exactly one of (1) `values` (new entries to append) with `citations` grounding them, verified the same way `propose` verifies any other quote — immediately, on that field alone, not deferred to commit time — or (2) `confirmed_absent: true` with a `reason`: the agent's own testimony that the field genuinely does not apply, never itself verified by Polaroid (the same epistemic category `escalate`/`blocked` already are for walkthroughs). There is no third way to leave a field undecided.
- **Peek is always safe.** Calling `propose_advance` with no `outcome` reports the draft's current state unchanged and never attempts a commit, even when nothing is left undecided — the same convention `start`/`advance` already guarantee.
- **The moment every field is decided, that same call auto-commits.** Through the identical checks single-shot `propose` already runs (citation self-consistency, ADR-0057 completeness, the non-vacuous composition gate, the novelty-diff). A failure (still vacuous, or redundant) is returned as the specific error, and the draft stays open with every earlier answer intact, so the agent can correct exactly the field responsible and call `propose_advance` again — `next_field` is empty and `status` is `"in_progress"` in this state, meaning "answered but not yet committed, retry needed," distinct from a pure peek's own empty-`next_field`/`in_progress` pairing. On success `status` is `"complete"` with the new `snapshot` and `key`, and the token then behaves exactly like a closed or expired one on any later call (`not_found`, no trace).
- **`close: true` abandons the draft immediately**, whatever its status, with no commit and no trace left behind — the same as letting it expire.
- **Scoped to existing Procedures only.** No equivalent exists yet for `new_concept`, `new_claim` or `new_orchestration`; use single-shot `propose` for those. Drafts are ephemeral, SQLite-backed state (mirroring walkthroughs), not visible to any operator surface and not reasoning-wired: `Compose` does not yet read the `*Complete` flags, so a composition pair already vacuous before a draft starts stays open to the same #173 check regardless of how the draft's fields were answered.

Requests can fail with these codes: `invalid_request` (a missing or malformed field, an unknown `field` name, neither or both of `values`/`confirmed_absent`, a missing or unverifiable citation), `not_found` (an unknown or expired token, or a key that does not exist), plus `propose`'s own commit-time codes (a completeness or non-vacuous-composition failure, or a redundant candidate) when the auto-commit itself is attempted and fails.

## Resources

All resources are read-only and returned as `application/json`, with the same body as the matching tool.

| URI template | Same as |
| --- | --- |
| `polaroid://procedures/{id}` | `get_procedure` with `id` |
| `polaroid://procedures/{id}/versions/{version}` | `get_version` |
| `polaroid://bindings/{id}` | `get_binding` |

An unknown record, or a version that is not a number, gets the protocol's resource-not-found error.

## Connecting a client

Start the daemon (`bin/polaroidd`), then point the client at the URL. This repository ships the VS Code configuration in `.vscode/mcp.json`; for another workspace, add the same file:

```json
{"servers": {"polaroid": {"type": "http", "url": "http://127.0.0.1:7417/mcp"}}}
```

**After upgrading `polaroidd`, restart the server in the client.** Some clients cache the tool list despite `ttlMs: 0`. VS Code Copilot chat (VS Code 1.137) keeps it until **MCP: List Servers → polaroid → Restart**, and the new tools appear from the next chat request on.

Verified clients (2026-10-09):

| Client | Result |
| --- | --- |
| VS Code Copilot chat (VS Code 1.137, bundled `@github/copilot` runtime) | Works: the 17 tools of the time discovered, full workflow run from chat. |
| Go SDK v1.8.0 client | Works; used by the automated tests. |
| TypeScript SDK 1.32.1, MCP Inspector 2.10.1 | Work at 2025-11-25 since ADR-0016: 20 tools listed, tools called, no session. Before it they were refused. |

Other clients that support streamable HTTP take the same URL. The client must support protocol revision 2026-07-28 or 2025-11-25.
